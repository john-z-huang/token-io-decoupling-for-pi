# TypeScript / JavaScript 代码规范

## 1. 核心目标

所有新增和修改的 TypeScript / JavaScript 代码，包括生产代码与测试代码，必须优先保证人工可理解性、可审查性和可维护性。

代码通过编译、Lint 和自动化测试只是最低要求，不代表代码质量符合要求。

始终遵循以下原则：

- 优先保证代码简单、直接、显式，而不是追求最少代码行数。
- 代码应使熟悉项目的开发者能够快速理解其职责、数据流、控制流和边界条件。
- 不得使用复杂抽象、技巧性语法或过度封装来减少表面代码量。
- 不允许以自动化测试通过为理由忽略代码复杂度问题。
- 人工评审友好性与功能正确性具有同等重要性。
- 不得为满足静态指标而采取降低实际可读性的形式化修改。

## 2. 代码规模与复杂度

### 2.1 生产代码限制

新增生产代码应遵守以下限制：

| 指标 | 上限 |
|---|---|
| 单个代码文件 | 300 行 |
| 单个函数或方法 | 50 行 |
| 圈复杂度 | 10 |
| 认知复杂度 | 15 |
| 控制流嵌套深度 | 3 层 |
| 函数参数数量 | 3 个 |
| 函数内语句数量 | 15 条 |
| 嵌套回调深度 | 3 层 |

行数统计不包含纯空行及纯注释行。

这些限制适用于新增代码。存量代码按照第 9 节的渐进治理规则处理。

超过限制时，应优先考虑简化控制流、划分职责、消除重复和重新设计数据结构，而不是直接放宽限制。

### 2.2 复杂度控制

- 每个函数应具有单一、明确的职责。
- 优先使用 Guard Clauses、Early Return 减少嵌套。
- 避免多层 `if/else`、循环嵌套和 `try/catch` 嵌套。
- 避免嵌套三元表达式。
- 复杂条件应提取为有业务含义的布尔变量或命名函数。
- 不要将复杂逻辑压缩进链式调用、逻辑运算符或单行表达式。
- 对复杂分支流程，优先使用清晰的状态建模、显式分支或职责明确的策略实现。
- 不得通过增加无意义的辅助函数来隐藏复杂度。
- 函数拆分之后，调用关系和整体业务流程必须比拆分之前更容易理解。

### 2.3 文件与模块拆分

- 一个模块应围绕一个清晰且内聚的职责组织。
- 不得将多个不相关的业务流程放入同一文件。
- 当模块职责过多时，应按照业务能力或数据流边界进行拆分。
- 不得通过创建大量仅转发参数的函数、碎片化文件或无意义的 `utils` 模块来规避行数限制。
- 不要为了减少文件行数而引入不必要的抽象层、继承层或间接调用。
- 拆分后应确保关键业务流程可以通过少量、语义清晰的函数调用理解。
- 优先保持高内聚、低耦合，避免循环依赖。

## 3. TypeScript 类型与接口设计

- 优先使用清晰、明确的类型表达业务含义。
- 不得为了快速通过类型检查而使用 `any`、不安全的类型断言或 `@ts-ignore`。
- 对不可信的外部输入，优先使用 `unknown` 并进行必要的验证和类型收窄。
- 为公共接口、重要业务数据和跨模块边界定义清晰的类型。
- 避免重复定义相同的业务类型。
- 避免为简单问题引入复杂的条件类型、递归类型或多层泛型。
- 泛型、类型工具和高级类型技巧必须能够显著提高正确性或可维护性。
- 当高级类型明显增加理解成本时，优先选择更直接的类型定义。
- 不得为了满足函数参数数量限制而将互不相关的参数强行放入一个对象。
- 不得新增没有实际需求的抽象接口、泛型参数或可扩展配置。

## 4. 注释与文档

### 4.1 注释语言

遵循项目已有语言规范：解释性注释及 Docstring 优先使用简体中文，代码标识符继续使用规范的英文名称。

### 4.2 必须解释的内容

对于下列非显而易见的逻辑，应提供必要的注释：

- 复杂业务规则及其设计原因。
- 不容易从代码推断的边界条件。
- 特殊算法、性能优化和兼容性处理。
- 并发、异步、重试、缓存和状态一致性方面的约束。
- 重要的安全要求和异常处理决策。
- 看起来可以简化但实际上存在业务限制的实现。

### 4.3 注释质量要求

- 注释应解释为什么这样实现，而不是机械复述代码执行了什么。
- 不要给每个变量、赋值、条件和循环都添加注释。
- 不得使用长篇注释代替代码重构。
- 如果一个函数必须依靠大量解释才能理解，应优先考虑改善其结构。
- 注释必须与实际代码行为保持一致。
- 不得使用含糊的注释，例如「处理数据」「特殊逻辑」「兼容处理」，而不说明具体原因。
- 重要公共接口应在必要时说明输入约束、输出语义、可能的错误及副作用。

## 5. 测试代码可读性

测试代码也是需要人工审核和长期维护的正式代码。

**测试优先遵循 DAMP（Descriptive and Meaningful Phrases）原则：允许适度重复，以换取独立、清晰、容易理解的测试。**

### 5.1 测试规模

- 单个测试文件原则上不超过 400 行。
- 单个 `test()` / `it()` 测试用例建议不超过 50 行。
- `describe()` 嵌套层级原则上不超过 2 层。
- 一个测试用例应验证一个明确的业务行为；同一行为可以使用多个相关断言。
- 测试数据、执行动作与预期结果应能在局部上下文中直接理解。
- 测试的长度与复杂度不能仅通过隐藏实现细节来降低。

### 5.2 测试结构

- 优先使用 Arrange–Act–Assert 组织测试。
- 测试名称必须明确描述场景和预期行为。
- 测试名称不得仅使用 `works`、`should work`、`test1`、`handles case` 等模糊表达。
- 应明确区分正常路径、边界条件和错误路径。
- 预期值应尽可能显式给出，避免通过复制被测算法计算预期结果。
- 测试失败时，应能够从测试名称与断言直接判断出现问题的行为。
- 避免复杂的测试控制流，以及不必要的条件判断、循环和异常捕获。

### 5.3 测试辅助函数

- 仅提取真正具有复用价值且语义清晰的测试辅助函数。
- 可以将无关的对象构造细节隐藏在 Factory 或 Fixture 中。
- 不得将测试的关键输入、重要操作或预期结果隐藏在公共 Helper 内部。
- 不得构建需要阅读多个文件才能理解单个测试的复杂测试框架。
- 允许重复少量简单的测试准备代码。
- 不得为了追求 DRY 而牺牲测试的局部可理解性。

### 5.4 测试独立性

- 每个测试必须能够独立运行，不依赖其他测试的执行顺序。
- 避免跨测试共享可变状态。
- Mock、Fake Timer 和其他全局状态必须得到适当恢复。
- 优先验证可观察的业务行为，而非内部实现细节。
- 对外部服务、网络、时间或随机性等非确定性依赖进行必要隔离。
- 不得对被测模块本身进行 Mock 以规避真实行为验证。
- Mock 应保持简单且明确，不得形成难以追踪的多层调用链。

### 5.5 参数化测试与快照

- 只有在多个测试场景具有相同执行流程且输入输出关系清晰时，才使用 `test.each()` 等参数化测试。
- 参数化测试的数据表应能够直接看出输入和预期输出。
- 不得将复杂对象、回调和动态逻辑嵌入大规模参数化测试表中。
- 不得通过循环动态生成难以独立识别的测试案例。
- 避免使用大型 Snapshot 代替明确断言。
- 对重要业务结果，优先断言具体字段、状态及可观察行为。
- Snapshot 必须足够小，以便人工审核其变化。

### 5.6 测试覆盖要求

对于修改的业务行为，应根据风险覆盖：

- 正常执行结果。
- 关键边界条件。
- 重要错误和异常路径。
- 必要的状态变化与副作用。
- 已修复问题的回归场景。

不得为了提高覆盖率而生成没有实际价值的测试。

不得仅验证函数被调用，而忽略真正重要的业务结果。

测试用例的数量不等于测试质量。

## 6. 可评审的实现方式

### 6.1 优先选择简单实现

当存在多种可行方案时：

- 优先采用符合项目习惯的直接实现。
- 避免不必要的设计模式、抽象基类、依赖注入层和配置驱动机制。
- 不得为未经确认的未来需求提前构建扩展框架。
- 避免隐藏控制流的动态派发、反射及复杂元编程。
- 避免为了减少重复而构建比重复本身更复杂的抽象。
- 对关键业务状态的变化和副作用，应保持清晰、显式。

### 6.2 数据流和错误处理

- 输入、转换过程与输出应容易追踪。
- 避免跨多个模块隐式修改共享状态。
- 避免函数在名称和类型无法体现的情况下产生重要副作用。
- 异步流程优先使用明确的 `async/await`，并遵循项目的并发设计要求。
- 不要通过过度压缩的 Promise 链隐藏错误处理。
- 不得使用空的 `catch` 或无说明地吞掉异常。
- 对可恢复错误与不可恢复错误采用明确的处理策略。
- 不得为了减少代码行数而删除必要的错误处理。

### 6.3 防止虚假简化

以下行为明确禁止：

- 将一个复杂函数机械拆成大量无语义的小函数。
- 使用嵌套三元表达式替代清晰的分支结构。
- 将复杂逻辑转移到难以阅读的配置对象。
- 使用动态调用或间接映射隐藏实际控制流。
- 将复杂业务判断分散到多个难以追踪的文件。
- 为规避复杂度检查而添加 Lint 禁用指令。
- 为通过检查而删除有价值的注释或测试。
- 引入仅用于满足指标、没有实际设计价值的抽象。

代码质量应以整体理解成本衡量，而不是只看单一指标。

## 7. 变更规模与人工评审

- 每次任务应聚焦于一个明确、可独立验证的目标。
- 在保证变更完整性的前提下，建议单次变更总量不超过 300 行，包括生产代码与测试代码。
- 当变更超过 500 行时，应主动评估是否能够拆成多个独立、可审核的变更。
- 不得将无关格式化、目录重组或大规模重构混入功能修复。
- 不得为了满足变更行数要求而省略必要测试。
- 如果任务天然无法拆分，应说明原因及评审重点。
- 仅修改完成任务所必需的代码，避免无关改动。
- 对复杂功能，优先按照独立业务能力或可验证阶段组织变更。

## 8. 代码生成后的自检

完成代码生成或修改后，按[静态代码检查](#静态代码检查)核验以下各项。已自动覆盖的条款以检查结果为准；其余按改动范围，结合真实调用关系、输入与失败路径、测试断言和用户验收条件核对。

1. 检查是否存在过长文件、过长函数和高复杂度函数。
2. 检查是否存在不必要的嵌套、抽象层及间接调用。
3. 检查命名、类型定义和模块边界是否清晰。
4. 检查注释是否解释关键设计意图且没有无意义内容。
5. 检查测试是否能通过局部阅读理解输入、操作和期望结果。
6. 检查新增代码是否引入不必要的依赖与复杂框架。
7. 检查是否存在为绕过静态规则而进行的机械拆分或规则禁用。
8. 执行适用的 Lint、类型检查和自动化测试。
9. 重新审视本次 Diff，确认改动范围合理且适合人工评审。

如果自检发现问题，应优先修正后再提交结果。

不得声称未实际执行的检查已经通过。

## 9. 存量高复杂度代码治理

本项目存在历史复杂度问题，因此采用渐进治理策略。

- 新增代码必须符合本规范。
- 未修改的历史代码不要求在每次任务中全部重构。
- 修改历史复杂函数时，优先缩小其复杂度或提取明确职责。
- 不得让修改范围内的高复杂度问题进一步恶化。
- 不得为了满足局部规范而引发大规模无关重构。
- 如历史代码超限且本次无法合理修复，应保留必要的功能兼容性，并明确说明剩余问题。
- 对无法满足的新代码约束，应说明原因、影响和替代方案，不得静默忽略。
- 规则例外必须有具体技术理由，并尽可能限制到最小范围。
- 不得自行大范围关闭静态检查规则或放宽项目阈值。
- 在保证行为不变的重构中，必须通过相关回归测试确认正确性。

目标是持续降低复杂度，而不是在一次任务中形式化消除所有历史问题。

## 10. Code Agent 最终交付规范

完成任务后，使用简体中文给出简洁的评审摘要，包括：

1. **变更内容**：完成了什么，以及主要影响哪些模块。
2. **实现方式**：关键设计与数据流，必要时说明选择原因。
3. **复杂度情况**：是否存在新增超限、特殊抽象或需要人工关注的复杂逻辑。
4. **测试情况**：新增或修改了哪些行为测试，以及实际执行的检查和结果。
5. **评审重点**：建议审查者重点检查的边界条件、兼容性或风险。
6. **遗留问题**：未解决的已知问题及原因；没有则无需单独展开。

不要将逐行代码说明作为最终总结，也不要重复粘贴大量已经生成的代码。

**最终判断标准：人工审查者应能通过阅读本次 Diff、相邻代码和相关测试，理解主要业务行为、判断正确性并识别潜在风险，而不必反复追踪大量间接调用。**

## 11. 功能模块化与目录结构规范

### 11.1 核心原则

TypeScript / JavaScript 项目必须优先按照业务领域和功能模块组织代码（Feature-Based / Domain-Based Organization）。

- 采用高内聚、低耦合的模块设计。
- 相关的业务逻辑、类型定义、数据访问、辅助函数和单元测试应尽量集中在同一功能模块内。
- 不得将大量不相关代码直接平铺在 `src/`、`lib/` 或其他单一目录下。
- 不得仅按照 `components`、`services`、`hooks`、`types`、`utils` 等技术类型组织整个项目。
- 优先使目录结构反映产品功能和业务概念，而非具体实现技术。
- 目录结构应帮助开发者快速定位功能，并在有限的文件范围内理解完整业务行为。
- 遵循框架已有的路由、入口文件及其他特殊目录约定，不得破坏框架规范。

**模块化的目标是降低代码理解成本，而不是增加目录和抽象层的数量。**

### 11.2 推荐目录组织方式

普通 TS/JS 应用可参考以下结构：

```text
src/
├── app/                   # 应用入口、初始化和组合逻辑
├── modules/               # 按业务功能组织的模块
│   ├── users/             # 用户模块
│   ├── orders/            # 订单模块
│   └── payments/          # 支付模块
├── shared/                # 真正跨业务模块复用的基础能力
└── main.ts
```

要求：

- `modules/` 下应按照业务功能建立子目录。
- 每个业务模块应具有明确的职责和边界。
- 一个模块包含与该功能直接相关的实现和测试。
- 模块内可以继续按照子功能进行拆分。
- 不要求所有项目使用完全相同的目录名称。
- 已有框架和项目约定优先，必要时可使用 `features/`、`domains/` 或其他语义明确的名称。
- 不得为了遵守示例而引入没有实际用途的目录。

### 11.3 模块内部结构

小型功能模块可以保持扁平结构：

```text
orders/
├── index.ts
├── cancel-order.ts
├── cancel-order.test.ts
├── order-policy.ts
└── order-policy.test.ts
```

当模块复杂度增长时，可根据实际职责继续拆分：

```text
orders/
├── index.ts
├── api/
├── application/
├── domain/
├── infrastructure/
└── tests/
```

以上子目录仅作为复杂模块的参考，不是必须实现的模板。

- 不得机械地为每个模块创建 `api`、`domain`、`services`、`repositories` 等目录。
- 只有存在明确的职责边界时，才引入新的子目录。
- 简单模块优先保持简单。
- 较复杂模块可以按子功能、用例或技术职责进一步组织。
- 同一模块内应尽量保持一致的组织方式。
- 不得通过增加不必要的目录层级隐藏逻辑之间的依赖关系。

### 11.4 目录规模和拆分原则

新增代码应避免目录持续膨胀。

采用以下建议作为目录健康度检查标准：

- 一个目录内的直属业务代码文件建议不超过 10～15 个。
- 当目录中出现多个独立业务职责时，应考虑按子功能建立子目录。
- 当目录内文件数量持续增加且定位困难时，应进行职责分析并考虑拆分。
- 业务模块内的目录嵌套一般建议控制在 3～4 层，框架约定目录除外。
- 不得通过创建大量只有一个简单文件的目录来机械满足数量限制。
- 不得仅为了减少目录文件数量而拆散本应共同维护的代码。
- 目录拆分应依据业务职责、模块内聚性和依赖关系，而不是随机分组。

上述数量属于项目可维护性建议，不是必须机械遵守的硬性限制。真正的评判标准是能否快速定位和理解代码。

### 11.5 模块边界和依赖方向

业务模块之间必须具有明确的依赖关系。

默认遵循以下原则：

- `app` 负责组合、初始化和协调业务模块。
- `modules` 包含具体业务能力。
- `shared` 提供与特定业务无关的通用基础能力。
- `shared` 不得反向依赖具体业务模块。
- 模块不得直接依赖其他模块的内部实现文件。
- 不得创建循环依赖。
- 模块之间应通过明确的公共接口进行交互。
- 对复杂的跨模块业务流程，优先由上层应用服务或协调模块进行组合。
- 不得通过全局可变状态或隐式副作用绕过模块边界。

依赖方向应尽量清晰：

```text
app
 ├── modules/orders
 ├── modules/users
 └── modules/payments
          ↓
        shared
```

实际允许的跨模块依赖应根据业务关系和项目架构明确约定，不要求所有功能模块完全独立。

### 11.6 模块公共接口

需要被其他模块访问的业务模块，应提供清晰且最小化的公共 API。

- 可使用 `index.ts` 或其他明确的入口文件定义模块对外暴露的能力。
- 对外只暴露必要的函数、类型和服务。
- 不得将模块所有内部实现无差别导出。
- 避免使用不受控制的 `export *` 聚合导出。
- 模块外部不得通过深层路径直接导入其他模块的内部实现。
- 模块内部优先直接引用本模块文件，避免通过自身公共入口反向导入造成循环依赖。
- 调整模块内部文件结构时，应尽可能保持公共接口稳定。
- 不得通过公共接口泄露大量内部实现细节。

公共接口存在的目的是降低模块之间的耦合，而不是制造额外的转发层。

### 11.7 Shared 代码管理

`shared` 目录只能保存真正通用且具有明确复用价值的代码。

允许的内容包括：

- 与业务无关的 HTTP 客户端及基础网络工具。
- 通用错误类型和基础错误处理机制。
- 通用日期、字符串及数据处理工具。
- 通用日志、配置和基础设施能力。
- 经确认可跨业务模块复用的 UI 基础组件。

禁止的行为：

- 将不确定归属的业务代码直接放入 `shared`。
- 将订单、支付、用户等领域专有逻辑放入全局 `utils`。
- 为避免模块划分而将业务逻辑统一放入 `common`。
- 将所有类型定义集中到全局 `types` 目录。
- 将所有常量集中到全局 `constants` 目录。
- 为了消除少量重复而过早提升为全局公共能力。
- 使 `shared` 逐渐演变为无明确职责的巨大业务模块。

**默认将代码保留在所属业务模块内，只有明确存在跨模块复用需求时才考虑提升为共享能力。**

### 11.8 测试代码目录组织

单元测试原则上应与被测试代码就近放置。

例如：

```text
orders/
├── cancel-order.ts
├── cancel-order.test.ts
├── order-policy.ts
└── order-policy.test.ts
```

- 不得把所有不相关的单元测试集中到一个不断膨胀的公共测试目录。
- 单元测试应能够快速定位对应实现。
- 模块内部测试可以访问本模块内部实现，以支持必要的单元级验证。
- 模块级集成测试应优先通过模块公共接口验证行为。
- 跨模块集成测试、端到端测试可以放入独立的 `tests/integration` 或 `tests/e2e` 等目录。
- 测试目录结构应与所验证的业务功能保持清晰对应。
- 不得为了目录形式统一而破坏既有测试工具或框架的发现机制。

### 11.9 防止过度模块化

模块化不是将每个函数都拆成独立文件。

以下做法应避免：

- 为每一个简单函数建立独立目录。
- 为简单业务流程引入多层 Service、Repository、Factory 和 Adapter。
- 创建大量只有转发能力的文件。
- 将一个业务流程拆分到过多无明确职责的模块。
- 为了复用少量简单代码而引入复杂的共享抽象。
- 让单个业务功能必须跨越大量目录才能理解。
- 将复杂度从函数内部转移为跨文件、跨模块的依赖复杂度。

应优先选择能让人工审查者以最少跳转理解完整业务行为的模块设计。

### 11.10 新增功能时的目录决策

Code Agent 在新增业务功能前必须：

1. 检查现有项目目录结构和模块划分。
2. 判断功能属于哪个现有业务模块。
3. 优先将相关代码放入已有模块，不得无故创建重复模块。
4. 如果功能具有独立业务职责且没有合适归属，应建立新的功能模块目录。
5. 在编写多个相关文件前，先规划它们的职责和依赖关系。
6. 保证测试文件与对应业务实现保持清晰关联。
7. 检查新增模块是否依赖其他模块的内部实现。
8. 避免将代码直接堆积到项目根目录或大型公共目录。

当新增功能涉及多个业务模块时，应明确每个模块的职责及跨模块协调方式。

### 11.11 现有目录结构的渐进治理

针对现有项目的复杂度问题：

- 不要求每次任务都重新组织整个项目。
- 新增代码必须遵循功能模块化原则。
- 修改已有功能时，应优先将代码放入其对应的业务模块。
- 当原目录已经严重膨胀时，应优先考虑在当前任务范围内建立合理的功能边界。
- 不得继续向明显失控的公共目录添加不相关代码。
- 对历史代码进行目录迁移时，应保持外部行为和公共接口兼容。
- 不得将大规模无关文件迁移混入普通功能开发。
- 涉及模块迁移时，应同步维护导入路径、类型声明、测试和相关配置。
- 必须通过适用的测试和类型检查验证迁移结果。
- 对暂时无法修复的架构问题，应明确记录，不得通过新代码继续扩大问题。

### 11.12 Code Agent 模块化自检

完成代码生成后，按[静态代码检查](#静态代码检查)核验已覆盖的导入和导出规则，并结合本次改动审查其余模块化要求。

1. 新增代码是否位于正确的业务模块中。
2. 是否有多个不相关的业务功能被放入同一目录。
3. 是否出现新的巨大公共 `utils`、`services`、`types` 或 `common` 目录。
4. 是否存在模块之间直接引用内部文件的情况。
5. 是否出现循环依赖或不合理的依赖方向。
6. 是否创建了没有必要的目录或抽象层。
7. 测试是否与相应业务实现保持明确对应。
8. 人工审查者是否能够快速定位某个功能的完整实现。
9. 模块化是否真正降低了整体理解成本，而不是仅增加文件数量。

最终交付总结中，对于重要的模块新增、拆分或迁移，应简要说明新的目录位置、模块职责、公共接口及依赖变化。

## 静态代码检查

在仓库根目录执行 `npm run lint`。当前命令只检查 `eslint.config.js`，不扫描已归档的旧扩展，出现错误或警告即失败。排版问题用 `npm run lint:fix` 修复后重新检查；该命令只应用布局修复。

规则由 `eslint.config.js` 和 `.prettierrc.json` 定义。对实际传入的适用文件，配置覆盖下列规则；不能把配置文件通过视为所有 JS、TS 和 MJS 均已检查。

| 规范条款 | 自动检查范围 |
| --- | --- |
| 排版 | Prettier 检查缩进、分号、引号、尾随逗号和 LF 换行；目标行宽为 110 列。 |
| §2.1 规模及复杂度 | 文件最多 300 行，函数最多 50 行（不计空行和纯注释）；圈复杂度最多 10、认知复杂度最多 15；控制流和回调嵌套最多 3 层，函数最多 3 个参数、15 条语句。 |
| §2.2、§6 控制流 | 检查嵌套三元表达式、部分多余的条件分支和无注释空块。 |
| §3 类型及标识符 | 检查类型导入、适用的 TS 对外边界类型、显式 `any`、`@ts-ignore`、非空断言、经 `unknown` 的双重断言及适用标识符格式。 |
| §6.3、§9 规则例外 | 禁用源码内联规则配置。 |
| §11.5–§11.6 模块 | 检查项目内可解析的运行时循环、自引用和未显式命名的 `export *` 再导出。 |

未覆盖的语义要求按 [代码生成后的自检](#8-代码生成后的自检)和 [模块化自检](#1112-code-agent-模块化自检)核对。
