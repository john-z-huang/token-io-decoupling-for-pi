### Session 语义

模式、拓扑、职责分配、生命周期、复用、替换、例外和不可用处理由当前工作流提供。职责名称本身不能授权新建 Session 或改变拓扑。

本文中的 Session 指宿主识别的完整 Session 生命周期，而不是一次用户/助手交互。同一 Session 的后续轮次、compact 或恢复都沿用其模式、数量和子代理身份。具有新 Session 身份的 Fork 开始独立生命周期，必须重新通过门禁。

Fork 会以新的根身份开启新的 Coding Session。在开展依赖工作前，必须重新通过模式/数量选择，即使来源 Session 使用过 Single-Agent 模式也一样。绑定到来源 Session 的子代理身份在 Fork 中属于其他会话：不得将其采纳为已创建子代理、复用或恢复、计入新会话预算，或提供给当前会话候选选择。新状态记录由[委派模式重入](../delegation/delegation-mode-reentry.yaml)和[委派状态记录](../delegation/delegation-state-record.yaml) owner 负责。

单代理 Coding 中，当前 Session 执行逻辑上的决策、实现、文档、Git 和允许的检查阶段；逻辑职责不表示存在独立 Agent。多代理 Coding 中，只使用当前工作流明确提供的子级执行上下文；具体 Session 隔离由运行环境决定：

```text
根父上下文 → Input-side Reasoning
已分配 Primary 子级上下文 → Primary Output
已分配 verifier 子级上下文 → Change Verification
已分配文档/Git 子级上下文 → Documentation/Comments & Git Operations
```

未分配的职责在独立子级上下文层面不可用。不得通过给同一上下文的工作改名来模拟独立性。
不得从预留名额数量推断职责；一个名额不会自动表示 Primary Output。只有审阅当前任务上下文和 Decision 后才能选择职责，再由职责选择与分配 owner 记录到未分配名额中。

### Primary Execution Session 与 Affinity

维持一个 Primary Execution Session：Single-Agent 模式下为当前 Session；Multi-Agent 模式下为已经创建且分配了 `Primary Output` 的子代理（如果存在）。在该子代理创建前，当前根 Session 仍是活跃决策上下文，但这不隐含创建 Primary 子代理。扩展支持持久身份与续接时，相关探索、实现、诊断、测试、修复和局部执行优先复用已分配的 Primary Session；一次性扩展不保证该能力。Session 应保持 sticky but not immortal；生命周期变化遵循当前工作流的已记录状态。

Session 隔离与 Git worktree 隔离不同。工作区和文件系统隔离条件由[上下文工作区边界](../context-exchange/context-exchange-workspace-boundary.yaml)定义；不得仅因复用 Session 就声称命中缓存或获得其他运行时收益。
