# 静态代码检查

本仓库的 JS、TS 和 MJS 遵循 [TypeScript / JavaScript 代码规范](TS_JS_CODE_SPECIFICATION.md)。自动覆盖的条款以检查命令的实际结果为准。Code Agent 根据当前变更判断需要语义和上下文证据的条款。

## 检查命令

- 在仓库根目录执行 `npm run lint`，检查当前维护的 JS、TS 和 MJS；旧扩展归档不运行 ESLint。错误或警告会使检查失败。
- 需要调整排版时执行 `npm run lint:fix`。ESLint 调用 Prettier 应用布局修复，其他规则仍会报告。修复后执行 `npm run lint` 复核。

## 已自动化的条款

规则由 `eslint.config.js` 和 `.prettierrc.json` 定义。ESLint 的行数检查排除空行和纯注释行。

| 规范条款 | 自动判定范围 |
| --- | --- |
| 项目排版 | `prettier/prettier` 校验 2 空格缩进、分号、尾随逗号、LF 换行、JS 和 MJS 单引号、TS 双引号等。110 列是 Prettier 的目标行宽。 |
| §2.1 文件和函数规模 | `max-lines` 对非测试文件限制 300 行，`max-lines-per-function` 对函数或方法限制 50 行，涵盖立即执行函数。 |
| §2.1 复杂度和嵌套 | 非测试代码的圈复杂度上限为 10，SonarJS 认知复杂度上限为 15。控制流嵌套和回调嵌套分别最多 3 层，函数参数最多 3 个，语句最多 15 条。 |
| §2.2、§6 控制流与错误处理 | `no-nested-ternary`、`no-lonely-if` 和 `no-else-return` 检查嵌套三元表达式及特定的多余分支。推荐配置中的 `no-empty` 报告没有注释的空块，包括空 `catch`。 |
| §3 类型与 §4.1 标识符 | TS 规则检查类型导入、适用的导出函数和公开方法的边界类型，以及显式 `any`、`@ts-ignore`、非空断言和经 `unknown` 的双重断言。标识符规则检查适用的声明、类成员和 TS 类型名称的字符范围。 |
| §6.3、§9 规则例外 | ESLint 禁用源码内联规则配置。 |
| §11.5–§11.6 模块依赖与导出 | `import-x/no-cycle` 检查项目内可解析的运行时导入循环，`import-x/no-self-import` 检查模块自引用。语法规则拒绝未显式命名的 `export *` 再导出。 |

### 存量问题与固定签名

旧扩展的 ESLint 抑制记录与固定回调签名例外仅留作历史记录，不用于当前维护范围。

## Code Agent 审查指令

根据实际变更选择以下审查项。格式、数值阈值和已匹配的语法模式直接采用命令结果。审查其余要求时，从改动的函数、调用者、测试和用户验收条件中取证，仅检查受本次变更影响的部分。

- **§1、§2.2–§2.3、§6 的可读性与行为**。沿入口追踪输入、分支、状态变化、副作用和失败后的恢复路径。判断函数职责是否明确，复杂条件是否可读，拆分后的调用链是否更容易理解。发现技巧性表达、过度抽象或吞掉异常时，按实际业务简化并补足必要的失败处理。
- **§3 的类型语义**。从数据来源核对外部输入的验证和类型收窄。评估断言是否有依据，公共类型是否表达业务含义并保持调用约定，泛型、参数对象和扩展接口是否有实际用途。
- **§4 的命名和注释**。判断英文名称是否表达职责，保留已有协议和外部接口的标识符。核对必要的中文注释是否说明设计意图、边界或兼容原因，并与当前行为一致。
- **§5 的测试设计**。判断测试名称能否说明场景和结果，结合实际调用核对别名或动态组织的测试分组。就地核对关键输入、操作和可观察断言，按风险验证正常路径、边界、失败及状态变化。检查夹具是否便于阅读，测试是否独立，Mock 和全局状态是否恢复，以及参数化或快照是否便于审查。
- **§7–§10 的改动范围与交付**。检查差异是否围绕任务目标，按 300 行的建议控制变更规模，超过 500 行时评估能否拆为独立的可评审变更。对受影响的存量问题核对是否加重，说明适用例外和兼容性影响。交付时记录实际执行的检查、结果和仍需核对的事项。
- **§11 的模块化与目录组织**。新增或迁移功能前先确认业务归属和公开入口。结合真实依赖判断模块内聚性、共享代码归属、跨模块内部引用和公共接口暴露范围，并核对超出静态导入图的依赖。根据目录职责和定位成本使用规模建议，检查测试与实现的对应关系及迁移后的兼容性。
